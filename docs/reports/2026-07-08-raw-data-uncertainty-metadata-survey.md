# Raw Data Uncertainty Metadata Survey

Motivated by preparing this dataset's Technical Validation section for a
Nature Scientific Data submission: **what measurement-uncertainty
information is actually present in the raw source files themselves** —
not in this repo's own decision docs or general instrument literature,
but literally in the metadata/headers of the files each parser reads, OR
in companion documentation (readmes, PDFs, data user guides) shipped
alongside them in the same raw archive? This matters because a Scientific
Data reviewer will expect either (a) per-variable uncertainty figures
traceable to the original data provider, or (b) an explicit, honest
statement of which sources don't provide one.

**Method**: for each campaign, identified the exact raw file(s)/instrument
subfolder(s) each parser actually loads (via `config.yaml` + the
`load_*()` functions in `parsers/<campaign>.py`), then (1) inspected one
representative data file per instrument directly, and (2) swept every
campaign's raw directory tree for companion documentation (`find data/raw
-iname "*.pdf" -o -iname "readme*" -o -iname "*.rtf" -o -iname "*.html" -o
-iname "*info*.txt"`) and read anything found. Three raw-format families
appear across the 15 campaigns:

- **ICARTT (.ict/.WB57)**: a standardized NASA aircraft-data format with a
  fixed header structure that includes named fields `UNCERTAINTY:`,
  `ULOD_VALUE:` (upper limit of detection) and `LLOD_VALUE:` (lower limit
  of detection) — when the data provider filled them in.
- **UND Citation FFI1001-derived** (`.CIT`, `.iphex`, `.mc3e`, `.mpace`,
  `.olympex`): a related but simpler NASA Ames FFI1001 header with
  per-variable descriptions and (sometimes) inline calibration
  slope/offset, but **no dedicated uncertainty field at all** — its
  presence or absence depends entirely on free-text comment lines the
  provider chose to include.
- **NetCDF (NCAR-RAF/Nimbus convention)** and **raw binary** (ARM):
  neither has a text-based uncertainty field; NetCDF variables carry a
  `DataQuality` attribute (qualitative, always `"Good"` in these files)
  and a `CalibrationCoefficients` array (linear raw-counts→engineering-
  units fit, not an uncertainty), and the binary ARM archive contains no
  text metadata whatsoever (`strings` on the decompressed file returns
  nothing).

### 1.1 Companion documentation sweep (readmes/PDFs beyond the data files)

A directory-wide search (`find data/raw -iname "*.pdf" -o -iname
"readme*" -o -iname "*.rtf" -o -iname "*.html" -o -iname "*info*.txt"`)
found companion documentation — beyond the data files themselves — for
**7 of the 15 campaigns**: ARM, ESCAPE, ISDAC, AIRS-II, ICE-L, IPHEX, and
MPACE (the last one only in the sense of a general format-spec readme,
not campaign-specific content — see below). The other 8 (ATTREX,
CRYSTAL-FACE-NASA, CRYSTAL-FACE-UND, MC3E, MIDCIX, OLYMPEX, POSIDON,
MACPEX) have **no** companion files anywhere in their raw directories —
for those, the ICARTT/UND-format header fields already covered in §1's
table are the complete picture; there's nothing else to check.

- **ARM** (`readme.txt`, `poellot-citation-t4-readme.txt`,
  `lu-asr2010.pdf`, `atsc-1520-0469_2002_059_3265_coscpd_2.0.co_2.pdf`):
  the binary-layout readme confirms `parsers/arm.py`'s `ARM_COLUMNS` and
  decode formula are correct against the original format spec (valuable
  for provenance, no uncertainty numbers). The Dong et al. (2002, *J.
  Atmos. Sci.* 59, 3265–3284) peer-reviewed paper documents real,
  citable FSSP cloud-droplet-probe uncertainty (**14% effective radius,
  25% droplet concentration, 30% liquid water content**, citing
  Baumgardner et al. 1985 and related instrument-calibration studies) —
  but for the FSSP instrument, not the Tair_C/P_hPa/Si/qv/Lat/Lon/Alt
  variables this pipeline actually extracts from ARM, so §1's ✗ for
  those specific variables stands.
- **ESCAPE** (`ESCAPE_SPEC_ReadMe_R0_10.2022.pdf`, in the
  `spec-learjet-state/` subfolder this pipeline's parser reads) —
  **the major correction**: a full instrument accuracy table (§2.0 of
  the PDF) gives, for every variable this pipeline extracts from ESCAPE:
  Temperature (Rosemount Model 102 & 510BH) **±0.5°C**, Dew Point
  Temperature (EdgeTech Chilled Mirror C-137, feeds Si/qv_chilled_mirror)
  **±1°C**, Aircraft Position (Aventech AIMMS-20 Dual GPS) **±10 m**,
  Altitude (West Star Aviation RVSM) **±60 ft (18.3 m)**. Each row also
  cites a peer-reviewed instrument reference (e.g. Lawson and Cooper
  1990 for the Rosemount thermometer). This is a complete, traceable,
  per-variable uncertainty table for an entire campaign — the strongest
  single source found in this whole survey — sitting in a file the
  `.ict` data file's own header pointed to (`UNCERTAINTY: Please contact
  PI`) but this survey's first pass never opened.
- **ISDAC** (`ISDAC_BulkData_v3_README.rtf`, `GeneralComments.rtf`,
  `README.html`, in the `strapp-convair_bulk/` subfolder this pipeline's
  parser reads): a long, detailed prose readme. It gives a real
  quantitative figure for position — "the uncertainty in the location
  obtained from looking at these plots is at maximum ~8 km," with
  specific flight numbers called out where it's worse ("a much higher
  error/uncertainty exists" — up to ~2 km of *additional* error — during
  specific flight segments, e.g. flights 21, 28, 35). For Tair_C (RSTem)
  and Si (ReHuI) it has qualitative-only language ("the best version of
  outside air temperature with good availability," "extensively checked
  against those provided by the airports at takeoff and touchdown"),
  which is validation context but not a numeric uncertainty — not
  counted as a ✓ in §1's table.
- **AIRS-II** (`README-info-201_001.txt`, `index.html`) and **ICE-L**
  (`README-info-105_004.txt`, `index.html`, in `nav-state-microphysics/`,
  the subfolder this pipeline's parser reads): both are NCAR/EOL archive
  metadata pages (DOI, citation, instrument list, temporal/spatial
  coverage) — useful for citing the dataset properly, but confirm rather
  than change the ✗ finding; no uncertainty numbers.
- **IPHEX** (`gpmcmiphx_dataset.pdf`, NASA GHRC "Data User Guide"): a
  detailed variable dictionary (confirms the calibration slope/offset
  values already found in the `.iphex` header, and gives the dataset's
  official DOI: `10.5067/GPMGV/IPHEX/MULTIPLE/DATA201`), but explicitly
  defers uncertainty/QC detail to three external instrument manuals (SEA
  M300, SPEC Inc. CPI, HVPS3/2DS) that are **not included** in this raw
  archive — confirms the ✗ finding rather than changing it.
- **MPACE** (`README.html`): not campaign-specific — this is the
  general **UND Citation "Format Specification for Data Exchange"**
  (Gains & Hipskind) that CRYSTAL-FACE-UND/IPHEX/MC3E/MPACE/OLYMPEX all
  use. It formally defines the header's `NSCOML`/`NNCOML` (special/
  normal comment line) fields as free-text space for "special problems
  or circumstances" / general dataset description — **confirming there
  is no dedicated uncertainty field in this format's specification**,
  not just that these particular files happened not to fill one in. This
  is useful primary-source backing for §2's claim about the UND-format
  campaigns.

**Two methodology lessons for treating this report as final**: (1) a
data file's own `UNCERTAINTY: Please contact PI`-style header field does
not mean the archive has no answer — check the containing directory for
readmes/PDFs before concluding a source is silent (ESCAPE). (2) Even a
real, found uncertainty figure needs to be checked against the *specific
variable* being cited — a companion doc can have excellent numbers for
one instrument (ARM's FSSP, ISDAC's position) and nothing for the
variables this pipeline actually extracts (ARM's Tair_C/Si/qv, ISDAC's
Tair_C/P_hPa/Si) — both must be checked, not just "does documentation
exist for this campaign."

## 2. Pattern: uncertainty availability tracks raw-format family, not campaign quality

This is the headline finding, and it's worth stating plainly for the
paper: **whether a variable has a documented uncertainty has nothing to
do with how "good" that instrument or campaign is — it's entirely a
function of which data-provider format the file happens to be in.**

- **All water-vapor/humidity instruments distributed as ICARTT `.ict`
  files report a quantitative uncertainty** (ATTREX's 3 hygrometers,
  MACPEX's 3 hygrometers, POSIDON's DLH, CRYSTAL-FACE-NASA's HW). Every
  one of these follows the same pattern: X% of reading, sometimes plus an
  absolute floor term (e.g. "5% + 1 ppm").
- **Every MMS-branded meteorology file (ATTREX, MACPEX, POSIDON — three
  different campaigns, evidently the same instrument/PI team, NASA Ames)
  reports the identical figure**: ±0.3 hPa, ±0.3K. This is a strong,
  reusable number: any campaign using an "MMS" file for Tair_C/P_hPa
  inherits this exact accuracy claim from the source.
- **Every UND Citation-aircraft campaign (CRYSTAL-FACE-UND, IPHEX, MC3E,
  MPACE, OLYMPEX — all Poellot/Delene, University of North Dakota) uses
  the same custom FFI1001-derived text format, and none of them contain
  an uncertainty field, in any instrument, ever.** This isn't
  instrument-specific — it's a property of that data provider's export
  format, which simply has no NCOM-equivalent field for it. 5 of the 15
  campaigns fall entirely into this "no uncertainty available" bucket by
  format alone.
- **NetCDF (AIRS-II, ICE-L) and ARM's raw binary are structurally
  incapable of carrying this information** in the files as delivered —
  NetCDF's own attribute schema here only encodes `DataQuality` (a
  boolean-ish flag, always `"Good"`) and calibration coefficients (a
  transform, not an error bound); ARM's binary has no text channel at
  all. ARM is a partial exception at the *directory* level, not the
  file level: a peer-reviewed paper packaged alongside the binaries
  documents FSSP-probe uncertainty (§1.1) — but that's uncertainty for a
  different instrument's variables than the ones this pipeline extracts,
  so it doesn't change the ✗ for Tair_C/P_hPa/Si/qv/Lat/Lon/Alt.
- **CRYSTAL-FACE-NASA's position data (`NP`) explicitly declines to
  answer** rather than omitting the field silently — "unknown accuracy...
  may not be adequate for precise calculations." ESCAPE's `.ict` header
  does the same ("Please contact PI"), but unlike CRYSTAL-FACE-NASA's
  case, ESCAPE's answer *does* exist — just one directory level up, in
  the companion PDF (§1.1). Both are more honest than the UND/NetCDF/
  binary formats' silent absence, but ESCAPE is the reminder that
  "explicitly deferred" isn't the same as "unavailable" — it's worth
  checking whether the deferral is answered elsewhere before concluding
  a variable has no traceable uncertainty.

## 3. Coverage gaps within otherwise-quantified instruments

Even where uncertainty is reported, it isn't always complete for every
variable a file feeds into this dataset:

- **MACPEX's MMS-FlightPath** gives altitude (±2.5–35 m, altitude-
  dependent) and airspeed (±1 m/s) uncertainty, but **not** Lat/Lon —
  those columns are unaccompanied by any figure despite the file
  providing them for other variables.
- **IPHEX's per-variable calibration coefficients** (slope/offset, e.g.
  "Static Pressure [hPa] {Calibration: slope = 207.08 offset = -0.71}")
  describe the raw-counts→engineering-units transform, not measurement
  uncertainty — easy to mistake for one at a glance, worth calling out
  explicitly so a reader doesn't conflate "this variable has a
  calibration" with "this variable has a stated accuracy."
- **ISDAC's position uncertainty (~8 km typical, from the companion
  readme, §1.1) covers only Lat/Lon** — Tair_C, P_hPa, and Si (RSTem,
  NPres, ReHuI) have no numeric figure anywhere in the data file or its
  companion docs, only qualitative validation language.

## 4. What this means for the paper's Technical Validation section

1. **A per-variable, per-campaign uncertainty table is honestly
   populatable for more of the dataset than the raw data files alone
   suggest** — ATTREX, MACPEX, POSIDON's hygrometer/MMS variables,
   CRYSTAL-FACE-NASA's HW, and (after §1.1's companion-doc sweep)
   **ESCAPE's full variable set** all have real, traceable numbers.
   CRYSTAL-FACE-NASA's position and ISDAC's position (partial) are
   honest non-disclosures/partial answers rather than silence. The
   remaining ~7 campaigns (CRYSTAL-FACE-UND, IPHEX, MC3E, MPACE,
   OLYMPEX, MIDCIX, AIRS-II/ICE-L's netCDF, plus ARM's core variables)
   have genuinely nothing in the raw archive — for those, the paper
   needs either (a) a citation to published instrument-accuracy
   literature external to this dataset (as
   `docs/decisions/2026-07-05-arm-cryo-masking.md` already did informally
   for ARM's Rosemount sensor, citing ±0.3–0.5°C from general literature,
   *not* from ARM's own raw file — worth being explicit in the paper
   that this number is not provenance-traceable to the raw archive), or
   (b) an honest "not available from the original data provider"
   statement.
2. **Don't present a single blanket "instrument uncertainty" table as if
   uniformly sourced** — mixing raw-file-derived numbers (ATTREX/MACPEX/
   POSIDON/ESCAPE) with literature-derived numbers (ARM) with
   "unavailable" (UND-format campaigns, NetCDF campaigns) in one table
   without marking provenance would overstate this dataset's
   traceability. A reviewer who spot-checks one of the "unavailable"
   cells against the cited source will find nothing there.
3. **The MMS ±0.3 hPa/±0.3K figure recurring identically across 3
   campaigns, and ESCAPE's full instrument accuracy table, are genuinely
   strong, citable numbers** for this dataset's most-used state variables
   — worth foregrounding in the paper rather than burying them alongside
   the "not available" cases.
4. **Always check the containing directory, not just the data file,
   before writing "not available" in a paper** — this is the single
   biggest lesson from this survey. ESCAPE went from "no uncertainty
   available" to "full accuracy table, every variable" purely by
   opening one more PDF sitting next to the data.

## 5. Caveats on this survey itself

- One representative file per instrument/subfolder was inspected, not
  every file — spot checks across a few flight dates per instrument
  (ATTREX, MACPEX) showed identical header text run-to-run, so this is
  assumed stable within an instrument for a campaign, but was not
  exhaustively verified across every single flight-date file.
- This survey only covers instruments/files each parser actually loads
  (per `config.yaml` + `parsers/<campaign>.py`) — several campaigns' raw
  directories contain additional unused instrument subfolders with their
  own companion docs (e.g. ESCAPE's `cfdc/`, `ccn/`, `nrc-aerosol/`;
  ICE-L's `dmt-caps/`, `cvi/`, `dri-ccn/`, `mission-summaries/`; ISDAC's
  `wolde-convair/`; MACPEX's `ULH/`, `CLH/`, `CIMS/`) that were found by
  the directory-wide search (§1.1) but not opened, since they don't feed
  any column in the merged L0/L1/L2 output.
- "No uncertainty field" means no *quantitative* uncertainty statement
  was found in the header/attributes/companion docs as delivered — it
  does not mean the original instrument team never characterized their
  instrument's accuracy, only that this particular archive doesn't carry
  that information forward for the specific variable in question.
- **Methodology note (now resolved, kept for transparency)**: this
  survey's first pass checked only the data-bearing files themselves and
  missed companion readmes/PDFs entirely (caught first for ARM, then
  generalized to all 15 campaigns via §1.1's directory-wide sweep — see
  the revision note at the top of this file). That sweep only opened
  files matching its search pattern (`*.pdf`, `readme*`, `*.rtf`,
  `*.html`, `*info*.txt`); a companion file with an unconventional name
  outside that pattern would still be missed.
